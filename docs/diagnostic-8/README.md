# Diagnostic 8 — RAK HOBO V3/V4/V5 source audit

Historical October 14 audit. The [October 15 final audit](V5-FINAL-AUDIT.md) adds V1/V2 and water-only history, the successful MX2001 response and final operating choices. Use the [current front page](../../README.md) for downloads.

Audit date: 2026-10-14. Repair base: `RAK-Water-Distance-HOBO-v5` at `b24de43d86ba` (the complete immutable SHA is in [provenance.json](provenance.json)). Repair branch: `repair/rak-hobo-v5-audit-20261014`.

**Status: software repair candidate; field root causes remain partly unverified.** Source inspection and host fault injection establish defects and rule out several proposed explanations. They cannot establish the physical identity of either MAC, reproduce the two reported failures, or prove unattended RF reliability. This document does not declare a hardware-validated repair.

## Why V4 failed while V3 appeared reliable

The audited water branches have the same `Bluefruit.begin(1,1)`, central bandwidth, callback registration, scanner interval, service/characteristic UUIDs and framework pin. Their `platformio.ini`, Nordic base flags and linker/toolchain selection are byte-identical. V4 does not change BLE event task initialization or thread stack sizes. Its single HOBO change records diagnostics at an already-existing watchdog escalation.

The `.noinit` diagnostic structure consumes 20 bytes and records existing recovery paths. The LPCOMP change affects entry to system-off sleep, not ordinary scanning or GATT discovery. Pairing now yields and uses rollover-safe elapsed time; disconnect waits are bounded. None establishes a new failure in the reported logger stages. Reverting these improvements would reintroduce unbounded waits without establishing why V3 worked.

Shared defects can explain failures across RAK stations **under particular conditions**, especially phone/serial shutdown disconnecting the central link and accumulated failures stopping watchdog feeds. They existed in V3 too. V4's new MaxBotix warm-up/read path also blocks the cooperative main controller for roughly 8–11 seconds per read (longer with fallback), but yields to FreeRTOS; it does not inherently prevent the independent BLE event task from completing GATT responses. This scheduling load is a test condition, not proof of either station's error. Changed sensor hardware, voltage during sensor power-up, distance, peer connection occupancy and exact installed binary must be checked on hardware.

**There is no source-supported exact explanation for the onset at V4 from the supplied observations.** No V4 failure trace or installed binary hash was provided. It would be misleading to name the 63-line platform diff as a proven cause. The repair addresses demonstrated shared ownership defects and makes a controlled return to the known-working setup path; comparing V3 and the repair on the same physical logger is still necessary.

## V5 execution context and event observer

Pinned Bluefruit `bluefruit.cpp:744–776` runs SoftDevice event handling on a dedicated RTOS BLE task. Lines 831–854 queue central connect/disconnect callbacks with `ada_callback`; lines 930–936 run Discovery and GATT handlers **before** the optional user event callback. `BLEDiscovery.cpp:72–105` requests discovery then waits on its message semaphore, with a 1,000 ms library discovery timeout. The deferred callback task can therefore wait while the BLE task supplies the response. This establishes compatibility for restoring the V3 callback path.

The main task can also wait on that semaphore. The audit does **not** prove that V5's execution context is intrinsically inappropriate. The change increases coupling to the main controller's sensor work and concurrent recovery state. The repair avoids that coupling during setup, uses an atomic setup flag, checks the physical link between operations and publishes `SEND_INIT` only after notifications are enabled. Discovery remains three attempts with the V3 500 ms settle and 350 ms retry delay; no timeout was increased.

The V5 raw event callback only copies diagnostics. It neither consumes events nor suppresses Bluefruit handlers; there is no other `setEventCallback` caller in this firmware. It is not a demonstrated interference cause. The repair retains a passive observer, adds the connection-timeout flag, and makes its shared diagnostic values atomic. It performs no blocking operation or scanner mutation on the BLE event task. Last-error storage remains distinct from verified model history.

## Recovery audit

- `recoveryPending`: originally waits for disconnect, then trips the watchdog at its 10-second deadline. Repair waits for the matching deferred disconnect callback, without resetting the radio for a normal BLE failure.
- `watchdogRecoveryPending`: originally suppresses further work while awaiting reset. Removed from HOBO code.
- `scanRestartRequested`: originally forces a stop/start. Repair attempts resume first; starts/stops are serialized with connection and cancellation decisions. A live central link prevents a new scan while a late connect callback is pending.
- `discoveryAttempts`: originally shared among main-loop stages. Replaced by local bounded V3-style retry counters.
- `scanRetryDueMs`: retains the existing five-second backoff and rollover-safe `reached()` comparison. Transient candidate rejection expires after five seconds; no permanent rejection is introduced.
- `connectionHandle`: now atomic; unrelated/stale disconnect callbacks cannot clear a different active handle. One central connection remains configured.
- `linkStartedMs`: the extra V5 setup deadline is removed along with main-loop discovery.
- `bootstrapStartedMs`: retained after successful callback setup. The existing 30-second protocol bootstrap limit remains; individual protocol read/status limits, model fallbacks and pointer synchronization remain. Sensor contention against this limit needs hardware soak testing.
- Unexpected `sd_ble_gap_connect_cancel()` errors are logged and retain the pending-attempt state rather than falsely opening a second connection procedure. Success and INVALID_STATE recover without reset. A persistent unexpected SoftDevice error is not proven recoverable by these host tests.

No new recovery loop, timeout increase or reset mechanism was added. Core hang detection and LoRa recovery watchdog remain. The pre-existing 12-hour scheduled node reboot is unchanged; this audit does not certify that policy as necessary.

## Candidate identification

Both MACs are merely candidates in the supplied evidence. Received RSSI measures the logger-to-radio path, not a successful two-way link. Interval zero and an unknown model are consequences of incomplete bootstrap, not logger settings that have been verified.

Advertising admits an Onset manufacturer payload (`C5 00`), exact HOBO service UUID, or a matching name. The latter two heuristics do not prove a physical logger's identity. Advertisement model hints select probe order; successful notification/protocol parsing identifies MX2001, MX2201 or MX2203. V5's last-verified history is explicitly separate from current identification.

V5 rejects reports whose SoftDevice `connectable` bit is false. A non-connectable advertisement cannot establish a legacy BLE connection; such a report may come from a legitimate HOBO in a temporarily non-connectable mode, but removing the filter would not make that packet connectable. No captured advertisement establishes that this filter wrongly rejects these stations. Both reported candidates progressed beyond scanning, so the filter did not reject the reports that produced these errors. The repair retains it and resumes scanning after rejection. `Central.connect(report)` forwards the full `peer_addr`, including address type; manual locks preserve the existing six-byte on-disk MAC schema.

Verify the logger inventory/label or HOBO app address, then test with other phone/app connections released. A successful firmware protocol read, correct model and expected measurement are required before treating a candidate as the intended logger. The audit does not remotely establish that either supplied MAC is the intended device.

## Seven-branch and build comparison

`provenance.json` records all seven exact commits and relevant Git blob IDs. Safe V3 and field V3 share the same HOBO blob; Safe V4 and field V4 share the same blob. Safe V3→V4 has extensive formatting changes but equivalent connect/discovery operations plus the diagnostic escalation call. Water V3 differs from Safe V3 chiefly in mesh reply ACK policy. The RAK translation-unit adapter is identical on all seven branches; its local Seeed macro exposes the shared implementation after dependencies are loaded under the real RAK board. There is no second HOBO scanner instantiated on the water target.

All seven use Nordic platform 10.11.0, framework commit `0fd295f13203e93df19d578073646ec32f2bf45a`, GCC ARM 9.3.1, C++17 and the same 2,048 stack definitions for loop/BLE/callback tasks. RAK uses board `wiscore_rak4631`, hardware model 9, `RAK_4631`, and one phone peripheral plus one logger central. Safe/field targets have different feature flags from the water target, so whole firmware images are not interchangeable feature comparisons. The repair builds both water sensor environments: `rak4631_sen0313_v5` and `rak4631_mb7388_v5`. The SEN0313 flag changes only the default when no valid saved sensor config exists.

V4 has overlapping water/HOBO build workflows that publish to the shared `field-self-recovery` download branch. They do not change BLE runtime source, but make binary provenance important. V5 has explicit two-sensor jobs and image checks. The dedicated repair workflow publishes only Actions artifacts; it never overwrites V3/V4/V5 or the existing download branch.

The disabled-phone TX-power workaround was also checked: in this pinned library `Bluefruit.setTxPower()` stores the advertising power, and advertising applies it with the ADV role. There is no evidence that its `-40` setting changes central initiation or connection power. It was therefore not changed or presented as a logger-link root cause.

## Preserved behavior and storage

MX2001 stage/temperature fragment decoding, MX2201 and MX2203 temperature decoding, model probe fallbacks, automatic transmission on write-pointer advancement, 30-second STATUS polling, interval synchronization, manual MAC locks and DM model reporting remain. V5's last verified identity and automatic-TX suppression protections remain. SEN0313, SEN0590, MaxBotix, sensor power switching, water distance/stage/discharge and explicit calibration commands remain.

The repair does not modify the distance `PersistentConfig` structure/version, calibration file paths, HOBO HBL1 lock format, HBI1 identity format, node identity, channels, encryption code, filesystem layout, linker limits, bootloader, SoftDevice or remote DFU module. It removes the automatic calibration-clearing migration after failed reads. Existing explicit sensor-change/calibration-reset commands retain their documented behavior and must not be used during an upgrade intended to preserve calibration.

App-only UF2 and application-only DFU ZIP verification must exclude bootloader, SoftDevice and filesystem payloads. Settings retention on a physical device across update/rollback remains a required hardware check, not a consequence of host tests alone.

## Matched Scout payloads

The separate autonomous Scout implementation was read from `Remote-Drone-Flashing-v2` at `37306158a64266fd05dfcd3bf01c5b47d0dc35fa`. It embeds raw-LZ4 compressed target firmware and the exact legacy DFU init packet. A generic OTA ZIP cannot change an already-embedded autonomous image. The repair therefore builds separate SEN0313 and MB7388 Drone UF2s using that unchanged implementation. The original compression builder verifies both the reference and firmware-style 64 KiB history decoders. The new verifier checks the compiled Scout contains the exact compressed array and DAT, that decompression equals the OTA binary, and that the expected target source SHA is present. These tests verify packaging, not airborne transfer or device selection. Existing Phase-2 serial upload also accepts the application-only ZIP.
